# Home-cloud cutover runbook

> **Status: COMPLETED 2026-08-02.** The cutover happened; production runs on
> the home-cloud k3s cluster and Render is decommissioned. Kept for the
> record of how it was done — nothing below is a pending action. This file
> lives in `runbooks/` (not `docs/`) on purpose: `docs/` is the public manual
> served at `/docs`, and a completed internal runbook enumerating cluster
> topology does not belong there.

One-shot runbook for migrating fountain's production data and traffic
from Render to the home-cloud k3s cluster. Pre-cutover scaffolding
(k8s manifests, Infisical project, image build, Flux onboarding) is
already done — see `decisions/` or the original PR for context.

**Estimated downtime: 15–30 min**, dominated by `pg_dump` + `pg_restore`
duration (depends on DB size).

## Prerequisites

- [ ] Staging stack is green at `https://fountain-hc.inevitable.fyi/health`
      (validates image, Infisical secret materialization, CNPG bring-up,
      cert, ingress) — DO NOT cut over until this is true.
- [ ] `kubectl` configured against home-cloud:
      `export KUBECONFIG=~/.kube/config-home-cloud`
- [ ] Local `pg_dump` / `psql` v17 installed: `brew install postgresql@17`
- [ ] Render dashboard open with the `fountain-db` external connection
      string copied to clipboard (External Database URL, *not* the
      internal one — your laptop isn't on Render's private network).
- [ ] Schedule a 30-min window and post a heads-up if anyone else uses
      the app.

## The cutover

### 1. Freeze writes on Render

Render dashboard → fountain service → **Suspend**. This stops the web
process; the DB stays up. New requests get a Render holding page until
DNS flips in step 6.

(Alternative: set `replicas: 0` via the API. Suspend is simpler.)

### 2. Dump from Render

```bash
# Replace with the External Database URL from the Render dashboard.
export RENDER_URL='postgresql://fountain:...@dpg-....oregon-postgres.render.com/fountain'

# -Fc = custom format, parallelizable on restore. ~1MB/s over WAN is
# typical for Render; a 500MB DB takes ~8 min.
pg_dump "$RENDER_URL" -Fc --no-owner --no-acl \
  -f /tmp/fountain-cutover-$(date +%Y%m%d-%H%M).dump

ls -lh /tmp/fountain-cutover-*.dump   # sanity check size
```

`--no-owner --no-acl` strip Render-specific role grants that won't
exist in the CNPG cluster.

### 3. Port-forward to CNPG

```bash
kubectl -n fountain port-forward svc/fountain-pg-rw 5433:5432
```

Leave running in a separate terminal. CNPG's `-rw` service routes to
the primary.

### 4. Get the CNPG password

```bash
# The fountain-pg-app Secret is auto-generated by CNPG on bootstrap.
export CNPG_PASS=$(kubectl -n fountain get secret fountain-pg-app \
  -o jsonpath='{.data.password}' | base64 -d)

# Sanity check connection
PGPASSWORD="$CNPG_PASS" psql -h localhost -p 5433 -U fountain -d fountain \
  -c 'SELECT version();'
```

### 5. Restore

```bash
# Wipe-and-replace. The staging boot ran migrations against an empty
# DB, leaving Ecto-managed schema in place. pg_restore --clean drops
# everything it owns first, then recreates from the dump — ensuring
# the prod schema/data fully replaces the staging Ecto migrations.
PGPASSWORD="$CNPG_PASS" pg_restore \
  -h localhost -p 5433 -U fountain -d fountain \
  --clean --if-exists --no-owner --no-acl \
  --jobs 4 \
  /tmp/fountain-cutover-*.dump

# Verify row counts match what you expect (compare to a query
# against Render before the dump if you want belt-and-suspenders).
PGPASSWORD="$CNPG_PASS" psql -h localhost -p 5433 -U fountain -d fountain <<'SQL'
SELECT 'users' AS table, count(*) FROM users
UNION ALL SELECT 'agents', count(*) FROM agents
UNION ALL SELECT 'environments', count(*) FROM environments
UNION ALL SELECT 'vaults', count(*) FROM vaults
UNION ALL SELECT 'conversations', count(*) FROM conversations;
SQL
```

You can stop the port-forward now.

### 6. Flip the staging host to the production host

Edit three files in the fountain repo and commit:

```bash
cd /Users/jake/dev/BinaryBourbon/fountain
sed -i '' 's/fountain-hc\.inevitable\.fyi/fountain.inevitable.fyi/g' \
  k8s/deployment.yaml k8s/ingressroute.yaml k8s/certificate.yaml

git diff --stat   # should show 3 files changed
git add k8s/
git commit -m "cutover: flip host from fountain-hc to fountain.inevitable.fyi"
git push origin main
```

Flux picks up the change within ~5 min (or `flux reconcile source git fountain && flux reconcile kustomization fountain` to force). cert-manager will issue a new cert for the production hostname — DNS-01 via Cloudflare; takes ~60s.

### 7. Swap Cloudflare DNS

The `*.inevitable.fyi` wildcard already points at home-cloud (verified:
`fountain-hc.inevitable.fyi` resolves the same as `guild.inevitable.fyi`).
A more specific record for `fountain.inevitable.fyi` likely exists
pointing at Render — delete it so the wildcard takes over.

```bash
# List records to find the specific fountain one
gh api 'zones/<zone-id>/dns_records?name=fountain.inevitable.fyi' \
  --hostname api.cloudflare.com -H 'Authorization: Bearer <cf-token>'

# Or just use the Cloudflare dashboard — DNS tab, search "fountain",
# delete the row that points at *.onrender.com or a Render IP.
```

If no specific record exists, you're done.

### 8. Smoke test production

```bash
curl -sSf https://fountain.inevitable.fyi/health   # expect 200

# Login flow validates GitHub OAuth callback (still pointing at
# fountain.inevitable.fyi/auth/oauth/github/callback — unchanged from Render)
open https://fountain.inevitable.fyi/auth/login

# Once logged in, open an agent and run a turn — exercises the
# envelope-encrypted vault/environment decrypt path. If
# MASTER_SECRETS_KEY carried over correctly, the turn runs; if not,
# you'll get a decryption error and need to roll back DNS.
```

### 9. Verify Stripe webhooks

The Stripe webhook URL doesn't change (still
`https://fountain.inevitable.fyi/api/stripe/webhook`), so webhooks delivered
during the cutover window will retry into the new env automatically.
Check the Stripe dashboard → Webhooks → recent deliveries for any 5xx
during the window.

## Rollback

If anything fails between steps 5 and 8:

1. **Re-point Cloudflare** back to Render (add the specific
   `fountain.inevitable.fyi` record again pointing at the Render service).
2. **Unsuspend the Render service.** Render's DB is untouched — it was
   only the *source* of the dump, never restored to. So bringing
   Render back online restores the previous prod state with zero data loss.
3. **Revert the host-flip commit** in fountain (optional, can leave
   the k8s manifests at fountain-hc since DNS now points elsewhere).

The home-cloud env stays running on `fountain-hc.inevitable.fyi` and
can be debugged at leisure.

## Post-cutover (~1 week later)

- [ ] Delete the Render service: `render services delete fountain`
- [ ] Delete the Render Postgres: `render databases delete fountain-db`
- [ ] Remove `render.yaml` and `.github/workflows/deploy.yml` (the
      Render deploy-hook trigger) from the fountain repo.
- [x] Optionally remove `fly.toml` if it's no longer relevant. (Removed
      2026-08-05 along with `PREREQUISITES.md` — it was an undocumented
      third deploy path with the hosted instance's domains baked in.)
- [ ] Rotate credentials exposed during the migration (see the
      original migration transcript — Stripe live keys, GitHub OAuth,
      Resend, Sprites, MASTER_SECRETS_KEY, the magpie admin client
      secret, the fountain-operator client secret). None left the
      local box but they sat in transcript while the migration ran.
